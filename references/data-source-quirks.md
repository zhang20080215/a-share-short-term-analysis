# push2.eastmoney API 数据源细节（田间技巧）

本文件记录了使用东方财富 push2 API 时的已知行为细节和陷阱。

## 1. f2 价格字段：÷1000 还是 ÷100？

### 板块排行 API (`fs=m:90+t:2` 或 `fs=m:90+t:3`)
```
f2=最新价
f3=涨幅%(×100)   → /100
f8=量比(×100)    → /100
```
- `f2` 已经是正常元单位（如 `f2=440` = 4.40元，即实际元×100）
- `f3` 和 `f8` 需要 `/100`（如 `f3=743=7.43%`, `f8=211=2.11`）

### 个股列表 API (`fs=m:0+t:6,m:0+t:80`)
```
f2=最新价(×100)   → /100
f3=涨幅%(×100)    → /100
f8=量比(×100)     → /100
```
- **`f2` 是实际值的100倍**（如 `f2=5802` = 58.02元），需 `/100`
- ⚠️ **2026-06-08 修正：** 此前本文件误写为 ÷1000。经与 `qt.gtimg.cn` 多票交叉验证（顺络电子 58.02元/f2=5802, 宝鼎科技 61.13元/f2=6113, 中国重汽 23.15元/f2=2315），确认个股列表 API 的 f2 也是 ×100 精度，与板块排行 API 一致。

**验证方法（每次不确定时）：**
```bash
# 同时拉取 eastmoney + qt.gtimg.cn 交叉验证
echo "Eastmoney f2 raw: $(curl -s 'https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=1&fields=f2,f12,f14&fid=f3&fs=m:0+t:6' | python3 -c 'import sys,re,json; print(json.loads(re.search(r"j\((.*)\)",sys.stdin.read(),re.DOTALL).group(1))["data"]["diff"][0]["f2"])')"
echo "qt.gtimg.cn price: $(curl -s 'https://qt.gtimg.cn/q=sz300105'|iconv -f GBK -t UTF-8|cut -d'~' -f4)"
```

## 2. pz 参数的实际上限

`push2.eastmoney.com/api/qt/clist/get` 的 `pz` 参数：

| 设置值 | 实际返回 | 行为 |
|:-----:|:--------:|:----|
| pz=20 | 20 | 正常 |
| pz=100 | 100 | 正常 |
| pz=200 | **100** | 上限100，超出被截断 |
| pz=500 | **100** | 上限100 |

**影响：** 当一个请求 `fs=m:0+t:6,m:0+t:80`（全市场主板+中小板+创业板，共3000+只股票）且 `po=1`（涨幅降序）时，只能拿到**涨幅最高的前100只**。

**解决方案：**
- 如果想筛选1-5%涨幅的股票，从这100只里过滤即可（上午10:00时，涨幅1-5%的通常在前100只内）
- 如果时间允许且需要完整数据，考虑使用腾讯 `qt.gtimg.cn` 逐只拉取

### ⚠️ pn={n} 分页仅返回前100只，无法翻页

**2026-06-17 实测确认：** `pn=2`（及更高页码）返回 **空响应**。push2 API 不支持分页——即使设置 `pn=2&pz=100`，也只返回总量统计但无内容。

```bash
# ❌ pn=2 返回空——无分页支持
curl "https://push2.eastmoney.com/...cb=j&pn=2&pz=100&..."
# → 返回 ''（空字符串）
```

**实际含义：** 全市场扫描时，你只能拿到涨幅排名**前100**的股票。对于极端分化行情（如高潮日），前100可能全都涨了7%以上，1-5%涨幅区间的股票不在返回结果中。这时降级到 `qt.gtimg.cn` 或 `cls.cn/telegraph` 是唯一选择。

### ⚡ 极端行情下前100只全部高涨幅的识别

**2026-06-17 实战案例：** 截至10:07，涨幅榜第100名的股票涨了约7.9%。这意味着**前100只中没有任何股票在1-5%区间**。

**如何识别：** 拉取全市场 `pz=100` 后，检查最后一只股票的涨幅：
```python
items = d['data']['diff']
last = items[-1]
last_pct = last['f3'] / 100
if last_pct > 7:
    print("⚠️ 极端分化日：前100只全部>7%涨幅，需降级方案")
elif last_pct > 5:
    print("⚠️ 分化显著：前100只中>5%涨幅居多，1-5%候选极少")
else:
    print("✅ 正常行情：前100只中包含1-5%涨幅的候选")
```

**影响：** 当触发此条件时，不要继续用 push2 尝试 pn=2（会返回空），直接降级到：
1. `cls.cn/telegraph` 找板块排名的实时 widget（浏览器的 JS 提取）
2. `qt.gtimg.cn` 批量查询各板块龙头股的实时行情
3. 从电报中人工提取候选股后，用 `web.ifzq.gtimg.cn` 拉 K 线算分位

## 3. 板块成分股查询的可靠性

```bash
# 使用 b:BKxxxx 查询板块成分股
fs=b:BK0448  # 通信设备 — ✅ 通常稳定
fs=b:BK1592  # 通信线缆及配套 — ⚠️ 有时返回空
fs=b:BK0546  # 玻璃玻纤 — ⚠️ 有时返回空
fs=b:BK1552  # 超市 — ⚠️ 不稳定
fs=b:BK1461  # 玻璃制造 — ⚠️ 不稳定
```

某些较小的板块（尤其是BK编号较大的）在 `b:` 查询下可能返回空响应。**这不是网络问题**，是 API 的内部行为。

### ⚠️ b:BKxxxx 返回错误数据（比空响应更危险）

**这是比空响应更隐蔽的问题：** 某些 BK 代码返回的板块名称与预期完全不符。

**实测案例（2026-06-10）：** `b:BK0990`（记忆中的"光刻机(胶)"板块代码）返回的是**物流/运输板块**的数据（山鹰国际、顺丰控股、东航物流等）。这不是空响应——数据完整但属于错误板块。

**原因：** BK 板块代码会随东方财富的板块结构调整而变更。静态的板块-代码映射表不可信任。

**排查方法：**
```python
# 发现b:BKxxxx返回的数据名称明显不对时，不要假定只是空响应问题
# 用返回数据中的股票名称快速判断：
# 请求光刻机板返回了山鹰国际(造纸)→绝对不对→立即降级
```

**安全规则：**
1. ❌ 不要依赖静态存储的 BK 板块代码（它们会变）
2. ✅ 用 `fs=m:90+t:2`（行业板块排行）或 `fs=m:90+t:3`（概念板块排行）先拿到**当前有效的板块代码**：响应中的 `f12` 字段就是该板块的最新 BK 代码
3. ✅ 然后用 step 2 拿到的 `f12` 再去请求 `b:BKxxx`——如果同一 session 内请求，代码是最新的
4. ✅ 如果 b:BKxxxx 仍然返回的数据前后矛盾（名称不符），立刻降级到 `qt.gtimg.cn` 批量查询已知龙头股

**降级方案：**
1. 如果 `b:BKxxxx` 返回空 → 尝试用 `m:90+t:2` 获取板块排行数据（这通常稳定）
2. 如果板块排行也失败 → 使用 `cls.cn/telegraph` 通过浏览器找热点（降级方案）
3. 直接使用 `qt.gtimg.cn` 批量查询该板块已知成分股

**板块成分股API可用性（2026-06-09 实测）：**

| 板块 | BK代码 | 可用性 |
|:----|:------|:------|
| PCB概念 | BK0877 | ✅ 可用（返回150只） |
| 模拟芯片设计 | BK1330 | ✅ 可用（返回34只） |
| 光刻机(胶) | BK0884 | ✅ 可用（返回96只） |
| 高带宽内存 | BK1152 | ❌ 空响应 |
| 半导体设备 | BK1326 | ❌ 空响应 |

**规律：** 概念板块（BK0xxx）通常比行业板块（BK1xxx）更稳定。BK1xxx 的 b: 查询失败率更高。

## 4. jCallback 参数必须用 `cb=j`

```bash
# ❌ 不要用
curl "https://...&cb=&...&fs=m:90+t:2"  # 返回空

# ✅ 必须用
curl "https://...&cb=j&...&fs=m:90+t:2"  # 返回 j({...})
```

`cb=j` 触发 JSONP 格式返回，没有这个参数（或 `cb=` 空值），API 基本返回空。

## 4b. `ut` 参数 — 行业板块 API 的高成功率补丁

**2026-06-26 发现。** 当 push2 行业板块 API (`fs=m:90+t:2`) 返回空响应时，添加 `ut=bd1d9ddb04089700cf9c27f6f7426281` 参数可能恢复数据：

```bash
# ❌ 可能返回空（即使 cb=j 也空）
curl "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=15&po=1&np=1&fields=f2,f3,f4,f8,f12,f14,f104,f105&fid=f3&fs=m:90+t:2"

# ✅ 添加 ut 参数后恢复正常
curl "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=15&po=1&np=1&fields=f2,f3,f4,f8,f12,f14,f104,f105&fid=f3&fs=m:90+t:2&ut=bd1d9ddb04089700cf9c27f6f7426281"
```

**关键行为：**
- **行业板块 API (`fs=m:90+t:2`) 需要 `ut` 参数的概率更高** — 本会话中不加 ut 返回空，加了才正常
- **概念板块 API (`fs=m:90+t:3`) 对 `ut` 的依赖较低** — 同一次会话中，不加 ut 也能正常返回概念排行
- **原因推测：** 行业板块的限流阈值比概念板块更严格，`ut` 参数使请求看起来像来自官方应用

**推荐做法：**
```python
# 行业板块 API 调用时，总是带上 ut 参数
api = "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=15&po=1&np=1&fields=f2,f3,f4,f8,f12,f14,f104,f105&fid=f3&fs=m:90+t:2&ut=bd1d9ddb04089700cf9c27f6f7426281"

# 概念板块 API 可以先试无 ut，不行再加
api_concept = "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=20&po=1&np=1&fields=f2,f3,f4,f8,f12,f14,f104,f105&fid=f3&fs=m:90+t:3"
# 如果空 → 再加 &ut=bd1d9ddb04089700cf9c27f6f7426281
```

**⚠️ 注意：** `ut` 参数值 `bd1d9ddb04089700cf9c27f6f7426281` 是一个硬编码的 token，可能会在未来失效。如果失效，请尝试从东方财富官网的 ajax 请求中提取最新的 `ut` 值。

**与 `cb=j` 的关系：** `ut` 和 `cb` 是独立的参数。`cb=j` 控制返回格式（JSONP vs raw），`ut` 控制请求身份认证。两个都要以正确形式带上。

# 概念板块更细粒度，能识别PCB概念、高带宽内存、CPO等主题

api_market = "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=100&po=1&np=1&fields=f2,f3,f8,f12,f14&fid=f3&fs=m:0+t:6,m:0+t:80"

- 用 `pn=2` 拉下一批100只
- 适当放宽涨幅下限到0.5%

## 6. K-line 量比 vs 板块API量比的差异

| 来源 | 含义 | 10:00 AM 的典型值 |
|:----|:----|:----------------|
| `qt.gtimg.cn` f[38] 换手率 | 今日成交股数/流通股本 | 2~5% |
| 板块API f8 (量比) | **每5分钟平均成交量**对比 | 1.5~3.0 (正常活跃) |
| K-line 今日量/30日均量 | 今日累计成交量/30日全天平均成交量 | **0.3~0.6** (因为只交易了30分钟) |

**常见误解：** 直接用 K-line 的「今日量/30日均量」在10:00时算出来只有0.5左右，会误判为「缩量」。但板块API的 f8 量比用的是**每5分钟区间对比**，所以10:00时也能正确反映活跃度（2.0=正常放量）。

**安全做法：**
- 用量比判断活跃度 → 用板块API的 `f8` 字段（÷100）
- 用 K-line 成交量判断趋势（量萎缩/放大相对于前几日同时间点）
- 不要在10:00时用「今日量/30日均量」这个指标做判断，至少等到13:00以后才有意义

## 7. ⚠️ push2.eastmoney 高不稳定性与重试策略

**2026-06-08 实战发现：** push2.eastmoney API 在单会话中可能**间歇性返回空响应**（`cb=j` 返回空字符串），即使前一个 curl 调用成功了。

**典型表现为：**
```bash
# 第一次调用 ✅ 成功返回数据
curl "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=20&po=1&fields=f2,f3,f8,f12,f14,f104,f105&fid=f3&fs=m:90+t:2"
# → 返回 j({...})

# 第二次调用 ❌ 空的（没有网络错误，就是返回空）
curl "https://push2.eastmoney.com/api/qt/clist/get?cb=j&pn=1&pz=100&po=1&np=1&fields=f2,f3,f4,f12,f14,f15,f20&fid=f3&fs=m:0+t:6,m:0+t:80"
# → 返回 ''（空字符串）
```

**这是 IP 级别的限流/反爬行为，不是偶然的网络抖动。**

### 同Session请求模式：第一次通常成功

**2026-06-10 实战发现：** 在同一个 agent session 中，push2 API 的**第一次请求几乎总是成功**，但第二次及后续请求大概率返回空。

```bash
# Session 内的典型模式：
# 请求1: 行业板块排行 → ✅ 成功（返回10条板块数据）
# 请求2: 概念板块排行 → ❌ 空（IP已被限流）
# 请求3: 个股全市场扫描 → ❌ 空
# 请求4: b:BKxxxx 成分股 → ❌ 空
```

**影响：**
- 如果首次调用成功拿到了板块排行，不要认为后续 b:BKxxxx 也会成功
- 尽量在**一次 curl 调用中完成所有板块数据获取**（比如概念+行业两个排行在两次curl内搞定）
- 如果板块排行成功了，个股扫描失败了——这是正常现象，不是数据不存在

**应对策略：**
1. 第一次调用拿到板块排行后，**立即将板块名称和涨跌幅记录**
2. 后续 b:BKxxxx 和个股扫描失败时，不重复重试，直接降级到 CLS 电报 + qt.gtimg.cn
3. 用 `execute_code` 可以让重试 + 降级在同一代码块内完成（最多2次重试，第3次仍失败就降级）

**实测可靠API（2026-06-11 更新）：**
| API | fs参数 | 可靠度 | 备注 |
|:---|:------|:------|:-----|
| 行业板块排行 | `m:90+t:2` | ✅ 中等 | **⚠️ 间歇性被限流。** 2026-06-11实测：同session中行业排行返回空，概念排行却成功。推荐双API并行，哪个返回用哪个 |
| 概念板块排行 | `m:90+t:3` | ✅ 较高 | 2026-06-11实测：概念板块API限流阈值比行业宽松。**优先尝试此API**，即使行业API空，概念可能正常 |
| 概念板块成分股 | `b:BK0xxx` | ⚠️ 中等 | BK0xxx概念较稳定。2026-06-11实测：BK1121、BK1173均成功 |
| 行业板块成分股 | `b:BK1xxx` | ⚠️ 较低 | 很多返回空 |
| 全市场个股扫描 | `m:0+t:6,m:0+t:80,m:1+t:2,m:1+t:23` | ❌ 不稳定 | 常返回空 |

### 实战策略：概念先行（2026-06-11）

当需要获取板块信息时，推荐**先尝试概念板块API**：

```python
# 推荐顺序：
# 1. 概念板块排行（m:90+t:3）— 限流最宽松，成功率最高
# 2. 行业板块排行（m:90+t:2）— 尝试但可能被限流
# 3. 如果至少一个成功 → 从排行中提取BK代码
# 4. 用BK代码查询b:BKxxxx成分股（限流后也可能工作）
# 5. 全部失败 → 降级到CLS电报 + qt.gtimg.cn

# 概念板块标签（如"第四代半导体""中芯概念""锂矿概念"）
# 比行业板块分类更精准反映当天炒作主题
```

## 8. push2.eastmoney.com 被本机IP封锁（2026-07-06 确认）

**所有通过本机直接访问push2.eastmoney.com的请求均失败：**
- curl: 返回空响应
- akshare Python库: ConnectionError（akshare底层也调push2）
- 浏览器fetch: 同网络层拦截

**唯一切实可行的替代方案：CLS电报页面（cls.cn/telegraph）。**
CLS页面底部渲染了行业板块排名+概念板块排名+资金流入数据，不依赖push2。

**验证过的无效替代方案：**

## 9. K-line API 的 key 命名陷阱

**2026-06-09 实战发现：** `web.ifzq.gtimg.cn` 的 K-line API 在返回 JSON 时，`data` 下的 key 包含 `sh`/`sz` 前缀（与请求参数中的 `param` 一致），**不是去前缀的纯数字代码**。

```python
# ❌ 错误写法（报 KeyError）
param = "sh600584"
resp = curl(f"https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param={param},day,,,60,qfq")
data = json.loads(resp)
k = data['data']['600584']['qfqday']  # KeyError: '600584' not found!

# ✅ 正确写法
param = "sh600584"
resp = curl(f"https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param={param},day,,,60,qfq")
data = json.loads(resp)
k = data['data'][param]['qfqday']  # param = 'sh600584'
```

**安全做法：** 不要硬编码 code 字段，直接用请求的 `param` 字符串作为 key 访问 `data['data'][param]`。
